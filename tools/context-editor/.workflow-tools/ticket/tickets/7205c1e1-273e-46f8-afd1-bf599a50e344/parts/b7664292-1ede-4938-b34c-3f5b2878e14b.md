## 2. Cross-module contracts (observed)

1. **`VoxelWorld` dirty-range → SVO upload/double-buffer contract.** `svo::VoxelWorld::take_dirty_ranges()` (`svo/mod.rs:223`) is called exactly once per frame by `svo::upload`'s `SvoUploadPlugin` system (`svo/upload.rs:175`), which drains dirty ranges and writes them into the `gpu` module's BACK buffer via `DoubleBindGroups`. The doc comment at `gpu/mod.rs` states the swap is "< 0.01 ms." Any restructure must preserve the once-per-frame drain invariant — `svo/upload.rs`'s own unit tests (lines ~258–280) assert `take_dirty_ranges()` returns empty immediately after a drain, which is the regression guard for this contract today.
2. **SVO / ray-march / depth / wireframe render-graph order.** `render/mod.rs`'s doc comment fixes the node order as `BufferSwap → ParticleCompute → SvoRayMarch → DepthBridge → UiComposite → WireframeOverlay`, implemented as a `ContextEditorLabel` enum with one variant per stage. This ordering is structural to the render graph, not incidental — `DepthBridge` explicitly depends on `SvoRayMarch`'s NDC-depth storage-buffer output, and `WireframeOverlay` is drawn last "with depth testing" against the composited result.
3. **Palette → `StandardMaterial`/PBR contract.** `world::theme::MaterialDef::to_standard_material()` (kernel-side) is called by `sandbox-app/src/bootstrap.rs::sync_palette_materials` (app-side, line ~473), which queries `(&PaletteMesh, &MeshMaterial3d<StandardMaterial>)` and rewrites `Assets<StandardMaterial>` each time the palette changes. This is a kernel→app boundary, not an internal kernel contract — the kernel provides the conversion function; the app owns the Bevy query/system that applies it.
4. **Dioxus atomics/events → Bevy systems bridge.** `ui/mod.rs::root_app` (the Dioxus root component) calls `crate::world().sidebar_content()` / `.inventory_content()`, where `world()` returns the global `Arc<dyn SandboxWorld>` set once by `lib.rs::launch()`. Concretely, this is a **static, one-directional call from Dioxus rendering into the `SandboxWorld` trait object**, not a live bidirectional event bus; `ui::interaction::InteractionBridgePlugin` and `ui::bridge::UiBridgePlugin` are the Bevy-side plugins that presumably carry the reverse direction (Dioxus event → Bevy system), but this pass did not trace their internals to confirm the exact queue/channel mechanism — **flagged as an evidence gap**, not asserted as verified.
5. **`sandbox-app` → `launch`/`build_kernel_app`/`SandboxWorld` contract.** `lib.rs::launch<W: SandboxWorld + Default>()` is the single public entry point; it sets the global `WORLD` static exactly once (panics on a second call, confirmed by its own doc comment), calls `dioxus::launch(ui::root_app)`, then (wasm32-only) calls `crate::world().run_bevy_app(build_kernel_app())`. `build_kernel_app()` (wasm32-only, confirmed by `#[cfg(target_arch = "wasm32")]` at `lib.rs:151`) assembles all 28 plugins into a fresh `bevy::prelude::App` with no world-specific resources — the sandbox-app (or any future `SandboxWorld` implementor) is responsible for inserting `VoxelWorld` and any scene-bootstrap systems before the app runs, per the function's own doc comment.

## 3. wasm/native feature parity — confirmed evidence gap

`kernel/src/lib.rs`'s `launch()`, `build_kernel_app()`, `apply_registered_preset()`, `register_world_presets()`, and `world_preset_names()` are all split `#[cfg(target_arch = "wasm32")]` / `#[cfg(not(target_arch = "wasm32"))]`, with the non-wasm32 arm reduced to a no-op stub in every case (e.g. `world_preset_names()` returns `Vec::new()` natively). The `cargo test -p context-editor-kernel` run executed in this pass (see §4) ran on the **native** target (Windows, non-wasm32) and therefore exercised only the native no-op stubs for these five functions — it did not compile or exercise `build_kernel_app()`'s 28-plugin assembly, `launch()`'s Dioxus/Bevy wiring, or any of the 8 additional `#[cfg(target_arch = "wasm32")]` gates found in `render/canvas.rs`, `render/mod.rs`, `splat/particle_splat.rs`, `simulation/character.rs`, `ui/bridge.rs`, and `editor/debug_overlay.rs`. **No wasm32 build or test run was performed in this pass.** This confirms, rather than merely repeats, the roadmap's stated evidence gap: wasm/native feature parity for the kernel's app-assembly path remains unverified.
