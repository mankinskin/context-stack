### Critical environment finding (blocks all render-dependent classifications)

Viewing the baseline PNG shows the Debug/Nexus-Terminal HTML chrome and a
static loading spinner — camera 0/0/0, FPS 0, CPU threads 0. An extended
investigation script (temporary, Playwright, not committed) reproduced the
exact same byte-identical capture after polling up to 25s for a non-zero FPS,
and again after relaunching Chromium with
`--enable-unsafe-webgpu --enable-unsafe-swiftshader --use-angle=swiftshader
--use-vulkan=swiftshader --ignore-gpu-blocklist`. Browser console/pageerror
capture shows the exact cause:

```
[warning] No available adapters.
[error] panicked at bevy_render-0.18.1/src/renderer/mod.rs:281:36:
Unable to find a GPU! Make sure you have installed required drivers!
[pageerror] unreachable
```

**Blocker**: headless Chromium (Playwright, this sandboxed execution
environment) has no WebGPU-capable adapter, with or without software-fallback
launch flags. The Bevy renderer panics (`unreachable` trap) before any frame
is rendered, so the WASM instance freezes with the Dioxus UI in its
default/pre-hydration state. The W3 harness's committed baseline is itself a
capture of this loading state, not of actual rendered voxel-world output.
This is an environment/tooling limitation of this sandboxed session, not a
sandbox-app code defect, and it is recorded per instruction rather than
worked around (no committed-harness changes, no fabricated pass/fail).

### Fixed defect: Wireframe Grid `WireframeData` never initialized

- **Pre-fix capture (code-level, deterministic, GPU-independent)**: grep across
  the entire kernel crate for `init_resource::<... WireframeData>` returned
  zero matches. `upload_wireframe_data` (`kernel/src/render/wireframe_overlay.rs`)
  takes `Option<Res<WireframeData>>`; when the resource is absent it always
  executes `buffers.index_count = 0; return;`. Because nothing ever calls
  `app.init_resource::<WireframeData>()`, this is the code's only reachable
  path — the grid can never draw a non-zero index count regardless of the
  Enable/Depth/Occupied-Only toggles. A new unit test
  `editor::debug_overlay::tests::wireframe_data_resource_is_initialized_by_plugin`
  was added and, run against the pre-fix code (`git stash` of the plugin.rs
  change only), **failed** with:
  `WireframeData must be initialized by DebugOverlayPlugin so the Wireframe
  Grid overlay can ever produce a non-zero index_count` — confirming the
  reproduction deterministically via `cargo test`, independent of the
  GPU-adapter blocker above.
- **Fix**: `context-stack/tools/context-editor/kernel/src/editor/debug_overlay/plugin.rs`
  — added `app.init_resource::<crate::render::wireframe_overlay::WireframeData>();`
  in `DebugOverlayPlugin::build`.
- **Post-fix capture**: same test now passes:
  `test editor::debug_overlay::tests::wireframe_data_resource_is_initialized_by_plugin ... ok`.
  Full suite: `cargo test -p context-editor-kernel` → 390 passed; 0 failed
  (389 pre-existing + 1 new).
- **camera_query.single() concern**: reviewed; exactly one `Camera3d::default()`
  spawn site (`sandbox-app/src/bootstrap.rs:112`) in a `Startup` system, which
  runs before the first `Update` in the same frame — no evidence of a
  multi-camera or zero-camera race. Classified **not-reproduced**.
