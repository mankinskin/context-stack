# Context-Read

## Legacy / positioned split

The row reader (`pipeline/`, `expansion/`, `request.rs`, `segment.rs`,
`input.rs`, its unit tests, the frozen v2 fixtures and
`legacy_reader_behavior`) lives in the crate
[`context-read-legacy`](../context-read-legacy/README.md)
(`context_read_legacy::{read, ReadCtx, ReadSequenceIter, SegmentResult,
IntoReadInput}`). This crate is the positioned reader `context_read::read`
([reader plan](agents/plans/20261122_PLAN_POSITIONED_READER.md), phases
R1–R3: `segment.rs`, `root.rs`, `forward.rs`, `expand.rs`, `read.rs`). Black-box tests:
`tests/reader_behavior.rs` and `tests/fixture_validation.rs` (v3 fixtures);
`tests/support/` holds `positioned.rs` (v3) and the shared `mod.rs`.

**Rule:** the legacy crates are frozen (no new code). New (positioned-model) code goes into this crate and must not depend on the legacy crates. Plan: `context-read/agents/plans/20261119_PLAN_POSITIONED_MIGRATION_PREPARATION.md`.

Graph reading and expansion operations for the context framework.
Provides ordered, recursive hypergraph operations for sequenced tokenized
data with structural overlap closure and ownership-safe accumulation.

## Features
- Ordered recursive hypergraph operations
- Sequenced tokenized data handling
- Graph complement operations
- Root-postfix expansion with immediate commits
- Block iteration for sequence processing
- Context-aware reading operations

## Key Concepts
- **Ordered Hypergraph**: Recursive graph structure for sequenced data
- **Root Anchor**: Structural postfixes of the latest committed root supply overlaps
- **Block Iteration**: Efficient sequence processing in blocks
- **Complement Operations**: Graph complement calculations

The [block expansion documentation](docs/README.md) describes the row
reader's root-postfix expansion and accumulation in
[`context-read-legacy`](../context-read-legacy/README.md#block-expansion-and-accumulation).

## Dependencies
- **context-trace**: Core graph structures and operations
- Standard Rust collections and iterators
- Test framework integration

## Development

### Tests and oracle fixtures

Positioned reader tests live in [`tests/reader_behavior.rs`](tests/reader_behavior.rs):
one test per v3 manifest entry, calling only `context_read::read` and
comparing the final graph with the v3 fixture via
`context_trace::positioned::diff`. The scenarios with provisional retention
(reader plan §5: `repeat_abcabca`, `repeat_ababa`, `insert_periodic`) are
`#[ignore = "provisional retention (reader plan §5)"]` until step 5.
`read_gate` reads every case of the read lane (below) and passes iff exactly
the expected deviations (`READ_DEVIATIONS`) fail; the worked examples of the
plan (§2) also assert their step traces (`context_read::read_traced`). The meta-test
`manifest_is_covered` (not ignored) requires a test for every manifest
entry, so a new v3 scenario must be registered in the `scenarios!` list.

Fixtures live in two lanes, each with its own scenario manifest of ordered
input corpora. The frozen legacy v2 row lane (`format_version: 2`) lives in
[`context-read-legacy`](../context-read-legacy/README.md#legacy-v2-fixtures-frozen);
this crate holds the positioned v3 lane:

| Lane | Manifest | Fixtures | Format | Used by |
|---|---|---|---|---|
| Positioned v3 | [`tests/fixtures/v3/scenarios.json`](tests/fixtures/v3/scenarios.json) (authoritative) | `tests/fixtures/v3/<name>.json` | `format_version: 3`, positioned covers (`context_trace::positioned::interchange::PositionedGraphSnapshot`) | `reader_behavior`, `fixture_validation`, context-trace positioned model tests, ngrams retention tests |

Late-retention scenarios have one fixture per completed-input prefix
(`<name>__1`, `<name>__2`, …), because a token may be retained only after a
later input.

#### Positioned v3 fixtures

The v3 files are generated by the [ngrams CLI](../ngrams/README.md), which
calls `ngrams::graph::parse_corpus` (not the reader). Regenerate them in a
release build (from the workspace root):

```bash
cargo run --release -p ngrams --bin ngrams -- \
  --file context-read/tests/fixtures/v3/scenarios.json \
  --out context-read/tests/fixtures/v3
# Generate one corpus to stdout:
cargo run --release -p ngrams --bin ngrams -- "ab" "bc" "abc"
```

Outputs are sorted, content-keyed JSON and deterministic; regeneration must
produce no diff. Oracle errors abort generation rather than yielding empty or
reader-derived expectations. `fixture_validation` requires exactly one v3
fixture per manifest entry, a corpus equal to the scenario inputs (order and
multiplicity), structural validity, and equality with a fresh `parse_corpus`
run. Each fixture records the corpus and one complete final
oracle graph in a top-level `vertices` object. To add a scenario, add its corpus to the v3
manifest, regenerate v3, the insert lane and the read lane (below), and review
the JSON diff against hand expectations.
Do not edit expected graph data by hand. Empty and single-character API
contracts are tested directly because the oracle does not support all such
corpora.

#### Insert fixtures (`v3/insert`)

The insert lane holds one oracle graph per positioned insert case
([insert plan](agents/plans/20261122_PLAN_POSITIONED_INSERT.md), task 3.1.1):
for every v3 scenario and every substring (2+ atoms) of a vertex string that
is not a vertex, the entry `<scenario>__<k>` with inputs `corpus + [query]`
(`k` numbers the scenario's queries from 1 in `(width, string)` order). The
enumeration asserts that every query has a unique minimal host. Regenerate
the lane after any change to the v3 fixtures (from the workspace root):

```bash
# Rewrite v3/insert/scenarios.json and delete the old case files:
cargo run -p context-insert --features test-api --example insert_manifest
# One oracle graph per case:
cargo run --release -p ngrams --bin ngrams -- \
  --file context-read/tests/fixtures/v3/insert/scenarios.json \
  --out context-read/tests/fixtures/v3/insert
```

`fixture_validation` requires exactly one file per insert manifest entry, a
corpus equal to the entry's inputs that extends its base scenario's corpus by
the query, and a manifest equal to a fresh enumeration of the current v3
fixtures. Tests load the cases with
`context_insert::fixtures::insert_cases()`.

#### Read fixtures (`v3/read`)

The read lane holds one oracle graph per read
([reader plan](agents/plans/20261122_PLAN_POSITIONED_READER.md) §9.1): for
every v3 scenario with `n ≥ 2` inputs and every `k ∈ 1..=n`, the entry
`<scenario>__<k>` with inputs `inputs[..k]`. Case `k` reads `inputs[k−1]` into
the graph of case `k−1` (the empty graph for `k = 1`). Regenerate the lane
after any change to the v3 manifest (from the workspace root):

```bash
# Rewrite v3/read/scenarios.json and delete the old case files:
cargo run -p context-read --example read_manifest
# One oracle graph per case:
cargo run --release -p ngrams --bin ngrams -- \
  --file context-read/tests/fixtures/v3/read/scenarios.json \
  --out context-read/tests/fixtures/v3/read
```

`fixture_validation` requires exactly one file per read manifest entry and a
manifest equal to the one derived from the v3 manifest. Tests load the cases
with `read_cases()` of the test support (`tests/support/read_lane.rs`).

Run the suites separately:

```bash
cargo test -p context-read --test reader_behavior
cargo test -p context-read --test reader_behavior read_gate
cargo test -p context-read --test fixture_validation
cargo test -p context-read --lib
```

Oracle mismatches are ordinary failing tests, not permissive subset
comparisons (the 6 legacy known failures of the frozen v2 lane are listed in
[`context-read-legacy`](../context-read-legacy/README.md)). A passing internal
mechanism test does not override a failing behavioral test.

```bash
cargo test          # Run tests
cargo doc --open    # Generate documentation
```

### Benchmarks

Criterion benches (`staging`, `staging_commit`, `staging_memory`) run with
`cargo bench -p context-read --no-default-features --features test-api`.

[`benches/oracle_speedup.rs`](benches/oracle_speedup.rs) compares the reader
with the n-gram oracle (`ngrams::graph::parse_corpus`) building the same
graph: the reader reads the inputs one by one into an empty graph, the oracle
builds it in one run over all inputs. Workloads are the v3 fixture corpora,
growing periodic and random inputs, and growing numbers of random inputs.
Every single run has a time budget (default 30 s): the oracle
is cancelled when it passes, the row shows `>30.0s (timeout)` with a lower
bound for the speedup, and larger sizes of that series are skipped. Results
go to `target/bench-results/oracle_speedup.csv`.

```bash
cargo bench -p context-read --bench oracle_speedup --no-default-features --features test-api
# Options after `--`: --budget <secs>, --no-timeout, --filter <substr>
cargo bench -p context-read --bench oracle_speedup --no-default-features --features test-api -- --filter periodic --no-timeout
# Unlimited runs by default (exact long-running numbers):
cargo bench -p context-read --bench oracle_speedup --no-default-features --features test-api,long-bench
```

`CONTEXT_BENCH_BUDGET=<secs>|none` sets the budget as well; command-line
options take precedence.
